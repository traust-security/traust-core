# traust-core

Python 3.11+ library. The platform API lives in `traust_core.v1`. Overview: [README.md](README.md).

## Design rules (read first — these override convenience)

- **One owner per capability.** Never implement a capability twice. Inconsistent data always means a second owner: remove it, never sync it.
- **Less is the goal.** One service per domain owns its use cases (reads and writes). Split a service only when it holds two responsibilities (e.g. `services/findings/`). No speculative helpers, no generic bases.
- **Place behaviour by responsibility:**
  - model: what a row is (one model per contract table, fields = columns) and rules about one value's own state (`Disposition.admit`); table models carry no behaviour
  - policy: rules needing config or spanning domains (`RatingPolicy`, `IdentityPolicy`)
  - service: use-case orchestration
  - repository: one per contract table — save, get, update and the named queries on that table
  - provider: anything outside the process (tools, forges, feeds, ledger, identity)
- **Domain boundaries.** A service never touches another domain's repositories; it calls that domain's service. Several repositories of your own domain in one service are fine — the line is whose repositories, not how many. Repositories never join across domains. Callers compose across domains by typed ID; composite reads are their own query object (`RepoStateQuery`).
- **The database owns identity and time.** Every record has `id` (UUIDv4), `created_at`, `updated_at`, generated by the database on insert (`RETURNING`); on update the contracts `<table>_touch` trigger keeps `updated_at` — the app never sets it (no SQLAlchemy `onupdate`). On SQLite, `uuid()` is registered by `create_database_engine`. Append-only tables (ledger events) stop at `id` (UUIDv4) and `created_at` — rows are never updated, so there is no `updated_at`. `id is None` = not saved yet; `add` returns the saved record. The app never mints IDs or timestamps. IDs are plain `UUID`, named `<entity>_id` (fields and parameters, matching the DDL's `<table>_id`); never a `str` ID, never a path as an ID, never a path in a signature. Don't re-declare `id` or add your own created/updated timestamps on an `Entity` or `AppendOnly`. Order comes from `created_at` (stamped per statement on both engines); ties break by `id`, which carries no order.
- **Same shapes everywhere.** Repositories: `get`, `find_*`, `list_*`, `add`, `update` (`add`/`update` return the saved record; append-only tables have no `update`). Skill doors: `prepare(...) -> <X>Input` and `record(doc, provenance)` (`@overload` per document). Rollups: `summary(filter, group_by)`; series: `timeline(filter, bucket)`. Deterministic document checks: `Lint`.
- **Services return domain results.** `JobResult` exists only at the engine/CLI adapter boundary.
- **One code path.** Solo (`traust …`, in-process), small group (`traust serve --with-engine`, one process) and scale (REST API, engine and runners as separate processes) run the same services; only the transport (in-process or REST) and the storage (SQLite + dir, or Postgres + object storage) differ. Never add a mode-specific branch of domain logic; the REST API holds none. CI runs service tests in-process and through the REST adapter, plus one end-to-end skill on SQLite with no server
- **Before adding a symbol, find the existing owner.** Extend it; if it truly can't own the new thing, say why in the PR. `grep -rn "NEED(" src` first.

## Agent files

- `AGENTS.md` (this file): rules, always loaded. `CLAUDE.md` imports it for Claude Code
- `.agents/skills/`: recipes loaded on demand (Agent Skills standard). `.claude/skills` is a symlink to it
- Writing Python here: load `python-patterns` (style, typing, errors) and `traust-core-patterns` (where code goes) before editing
- Edit only `AGENTS.md` and `.agents/skills/`; never fork content into `CLAUDE.md` or `.claude/`

## Before done

- First time in a clone: `make setup` (uv sync + git hooks via `core.hooksPath=.githooks`). Hooks: ruff on staged files (pre-commit), conventional subject (commit-msg), `make lint` + `make coverage` (pre-push). Don't bypass with `--no-verify`

- `make lint-fix` then `make test`; both must pass. `tests/v1/test_architecture.py` holds the placement rules; a failure there means the code is in the wrong layer, not that the allowlist needs widening. CI runs `make coverage`, which fails below 80% line+branch coverage (`fail_under` in `pyproject.toml`); stub bodies (`raise NotImplementedError`) are excluded, so new code must arrive with tests. Database changes also need `make db-up && make test-integration`; a new or changed query also gets a case in `perf/` and a `make perf` run (paste `.perf/report.md` into the PR)
- Tests that need Postgres are marked `@pytest.mark.integration`; `make test` excludes them
- Commits: conventional `type(scope): subject`
- Public repo: no deployment-specific hostnames or figures in code, tests or docs

## Versioning

- Everything public is under `traust_core/v1/`; tests mirror it under `tests/v1/`
- `v1` is not frozen yet: the platform API is reshaped in place
- No release machinery (no tags, CHANGELOG, VERSION bumps): consumers pin a git commit SHA, as core pins traust-contracts

## Layers

- `errors` → `contracts` → `models` → `providers` → `repositories` → `rendering` → `services` → `context` → `rest`; each imports only earlier ones (`tests/v1/test_layering.py`)
- One question per folder: `models` what it is and the rules about its own state, `providers` how we reach outside (tools, sources, feeds, process, clock), `repositories` how it is stored, `services` what we do with it (use cases + pure policies), `context` how it is wired
- Organised by role, then subject: `models/<section>.py` (table models + that section's service types), `repositories/traust/<section>/<table>.py`, `repositories/traust_ops/<table>.py`, `repositories/traust_ledger/<table>.py` (mirroring the contracts namespaces), `repositories/objects/` (bytes), `services/<subject>.py`; a service becomes a package only when it needs several modules (`services/findings/`)
- `models/base.py`: `Model` (strict, internal), `Dto` (tolerant, boundary data), `Entity` (`id`, `created_at`, `updated_at` — `None` until the database saves it), `AppendOnly` (`id`, `created_at` — rows are never updated)
- Tests mirror `src`: `tests/v1/<role>/test_<subject>.py`
- Pack policy (routing rules, cadences, lanes, skills, CLIs) stays in traust
- traust-core is the hub: every other traust repo depends on it, it depends on none of them. One exception: traust-ledger, a library of pure ledger functions (canonical bytes, Merkle, signing, verifying), imported only by `services/ledger.py`; traust-ledger never imports core. traust-contracts is data, read through `traust_core.v1.contracts`
- HTTP is in scope, in two places only: outbound calls live inside providers (forge, feeds, advisory APIs), and the inbound REST API
- **REST API:** `traust_core.v1.rest`, the top layer, installed by the `traust-core[rest]` extra and served by `traust-server`. Only `rest/` imports FastAPI, Starlette or uvicorn, and nothing imports `rest/`, so consumers never install them (`tests/v1/test_rest_isolation.py`). One package per domain (`rest/<domain>/`, a module per resource as it grows, listed in `rest/domains.py`); shared plumbing in `rest/common/`; a domain never imports another's routes, it composes through the services (`tests/v1/test_architecture.py`). A real service in front of the core services, with **no domain logic of its own** (rules live in the services, so the in-process path behaves the same). It must follow:
  - resources addressed by ID: `/findings/{finding_id}`, `/findings/{finding_id}/decisions`, `/orders/{order_id}/lease`; plural nouns, verbs only as HTTP methods
  - request and response bodies are the core models (R17), with an OpenAPI spec generated from them
  - one error shape everywhere (`application/problem+json`: type, title, detail, request ID), mapped from `traust_core.v1.errors`
  - lists are paged with a cursor (`Page`); filters are query parameters on the collection
  - every request carries a request ID (accept `X-Request-ID` or W3C `traceparent`, else mint one), returned in the response and in every log line it causes
  - one structured access-log line per request: method, route, status, duration, request ID, caller

## Contracts

- traust-contracts is a pinned dependency; read its data through `traust_core.v1.contracts` only, never import `traust_contracts`
- Nothing from traust-contracts is copied or generated into this repo
- Artifacts are named types in `models/artifacts.py` (`TriageArtifact`, ...); their fields come from the installed schema, never a hand-written copy
- Write with `ArtifactPublisher` (exact schema gate); read with `ArtifactPublisher.get(ArtifactId)`. `AnalysisResultsRepository.read(XArtifact, subject)` is legacy (path-keyed) until the Artifacts slice. No `json.load`/`.get()`/`json.dump` on artifacts
- Names: `models/artifacts.py` = what an artifact document is (`ArtifactDocument` and its named types); `models/assessment.py::Artifact` = the `artifact` table row; `repositories/objects/store.py` = raw bytes; `services/artifact_publishing.py` = the publish use case. Modules name the subject; the package names the role (no `_service` suffix)
- Core never tests the DDL: traust-contracts owns and tests its schema. Core tests repository behaviour against it
- Artifacts produced by the harness or an LLM go through `ArtifactPublisher`; nothing writes `analysis-results` files directly
- Protocols implemented outside core (`Materializer`, `Router` in `services/operations.py`) exist only for a decided pattern or backlog item; each gets an implementation in the repo that owns it
- Work is a service. Services return domain results; a `Materializer` (for traust-engine) and a CLI command (for LLMs) are thin adapters that validate input, call one service and turn its result into a `JobResult`; no logic in either

## Coding practices

**Comments and docs**
- The code explains itself: clear names, small functions, types
- Docstrings: optional, **1–2 lines max**, saying what something is for when the name can't. Never restate the signature, never list args/returns
- **Bloated comments and over-explaining are not allowed, at all.** No narrating what the code does, no multi-line comment blocks, no section banners, no commented-out code. If code needs explaining, rename or restructure it
- The one exception: a non-obvious *why* (a workaround, an external constraint), in one line
- `# NEED(<topic>):` marks an agreed platform need that is not built yet (up to 3 lines, the only multi-line comment allowed); `grep -rn "NEED(" src` before starting a slice and delete the marker when it lands
- API overviews belong in the README, not in module docstrings

**Logging and tracing** (you must be able to follow any request, run or order end to end)
- One logging setup, in `context`, driven by `Config`: level per logger, format (JSON for servers, text for a terminal), stderr plus a rolling file (size and retention configured). Nothing else calls `logging.basicConfig` or adds handlers
- Every entry point (REST request, CLI command, engine order, runner job) sets a correlation ID in a context variable. Every log line carries it, along with the order or run ID and the actor when known. Providers pass it on: an HTTP header on outbound calls, an env var for subprocesses
- Levels: ERROR = someone must act; WARNING = degraded or refused; INFO = state changes (record written, order moved, external call made, with duration); DEBUG = detail for diagnosis
- Log at boundaries (entry points, provider calls, repository failures), not inside every function. Log an error once, where it is handled; never log and carry on as if it succeeded
- Never log secrets, tokens or document bodies; log IDs, counts and digests instead

**Types and data**
- Type hints on every signature
- `Model` for internal objects (strict), `Dto` for boundary data (tolerant); frozen dataclasses for value objects
- Parse once at the edge; no bare `dict` across a function boundary
- Enums, not strings, for closed sets
- Unknown or unmeasured is `None`, never `0`

**Structure**
- Repository pattern: one repository per contract table: a `TableSpec` (columns once, built per dialect by `TableFactory`) and a `SqlTableRepository` subclass, on SQLAlchemy Core; no ORM mapped classes. The shared base gives only `add`/`get`/`update`; every other method is a named query on its table's module
- Domain objects never know about the database; rows map to models only inside repositories
- Services receive units of work, other services and providers through their constructor; they never open connections, build paths, read env vars or start processes
- A service declares the narrow section protocol it needs (`InventoryUnitOfWork`, `FindingsUnitOfWork`, …, or `TraustUnitOfWork` when it spans sections); `SqlTraustUnitOfWork` satisfies them all on one connection, so services that must write together share one instance and one transaction
- `Context` only at entry points; pass the specific dependency, not `Context`
- No `subprocess` outside `ProcessRunner`, no clock reads outside `Clock`
- Interfaces are `Protocol`s defined where they are consumed
- Pure logic (routing, report building) has no I/O

**Errors**
- Raise `traust_core.v1.errors` errors with context: what was being done, on what
- Wrap driver and library errors with `raise ... from e`; never swallow them

**Tests**
- Table repositories: behaviour tests in `tests/v1/repositories/tables/` — save, get, update and each query — on SQLite and Postgres through the `uow`/`seed` fixtures (`make test-repositories`). No tests that restate the DDL
- Stores and providers: contract tests that run against each implementation
- Pure functions get table tests
- Test names say the behaviour they protect
- A ported legacy scenario that belongs to a later slice is still written now, in its owner's test module, marked `@pytest.mark.todo("<slice>", legacy="<repo>/tests/<file>::<test>")` (skipped until that slice removes the marker). Never drop a legacy scenario silently
- Worked examples in `tests/v1/example/` are the pattern to copy; keep them current

**Scope**
- Smallest change that does the job; no drive-by refactors
- A new public module needs a README row and contract tests before merge
- Lint: line length 100; ruff E/W/F/I/UP/B/SIM/PTH/RUF

## Where we're headed

- Inside traust-core, new code uses the platform pieces below. Outside traust-core, everything goes through the platform API (`traust-client` or the SDK); old code is deleted by its domain's cut-over plan
- CI's drift ratchet (`python -m traust_core.v1.checks.ratchet`) fails a new hit (`path:line kind → use <API>`); baselines only shrink

| Hand-wiring | Inside traust-core, use |
| --- | --- |
| `sqlite3.connect` / `psycopg.connect` | `SqlUnitOfWork` / `SqlRepository` |
| `subprocess` | `ProcessRunner` or a tool provider |
| `os.getenv` / `os.environ` | `Config` / `Context` |
| `json.dump` / `write_text(json…)` | `ObjectStore` / `ArtifactPublisher` |
| `datetime.now()` / `datetime.utcnow()` | `Clock` |
| `requests` / `httpx` / `urllib.request` | a core provider (`SourceProvider`, `FeedProvider`, tool provider) |
